# Longspan · 技术复用与技术继承方案 v1.0

> 日期：2026-10-12
> 关联：`docs/MRD-Longspan.md`（v1.1）
> 结论：两个参考项目**都可以用**，但用法完全不同 —— ppt-master 是 MIT，**可以直接 vendor**；OpenMontage 是 AGPL-3.0，**只能借鉴架构、必须自研**。

---

## 0. 结论先行

| 项目 | 许可 | 能不能直接用 | 我们怎么用 |
|---|---|---|---|
| **hugohe3/ppt-master** | **MIT** | ✅ **可以直接用、可改、可闭源商用** | **直接 vendor 进 `skills/ppt-deck/`**，改造为我们的技能包。唯一坑：可选依赖 PyMuPDF 是 AGPL，只影响 PDF 源 |
| **calesthio/OpenMontage** | **AGPL-3.0** | ❌ **不能直接集成进闭源产品**（网络服务即触发传染，必须开源全部修改） | **借鉴架构与清单设计，用自研代码重新实现**。它的价值是"证明了怎么做"，不是"拿来的代码" |

**一句话**：**OpenMontage 是我们的架构教科书，ppt-master 是我们的现成 PPT 引擎。**

---

## 1. 两个项目分别是什么

### 1.1 ppt-master —— 把文档编译成原生可编辑 PPTX

- 定位：一个跑在 AI 编程助手里的**工作流（Skill）**，不是独立应用
- 核心管线：`源文档 → 建项目 → [模板] → Strategist → [Image_Generator] → Executor → 质量检查 → 后处理 → 导出`
- **技术核心：SVG 作为中间表示（IR）**
  - AI 只写 SVG（训练数据充足、可靠、人能在浏览器直接预览调试）
  - 后处理脚本把 SVG → DrawingML，调用 `python-pptx` 生成**原生 PowerPoint 形状**
  - 产物是**可点击、可编辑、可改色的真形状**，不是贴进去的图片
- 依赖全部是纯 Python，本机可装：`python-pptx`、`XlsxWriter`、`skia-pathops`、`uharfbuzz`、`PyYAML`、`Pillow`、`numpy`、`mammoth`、`markdownify`、`openpyxl`、`edge-tts`、`flask`
- 作者自己写了 **`harness + model = agent`** —— 这直接印证了 D1 对 "harness" 的理解

### 1.2 OpenMontage —— 把视频制片流程变成 Agent 可读的知识

- 定位：**首个开源的 agentic 视频生产系统**（GitHub 4 万+ star），同样跑在 AI 编程助手里
- 规模：12 条生产流水线、100+ 工具、500+ 技能文件
- 核心主张：**没有 Python 编排器**，"你的 AI 编程助手就是编排器"
- 统一阶段流：`research → proposal → script → scene_plan → assets → edit → compose`
- 免费栈即可出片：Piper TTS（离线配音）+ Remotion + HyperFrames + FFmpeg + 免费素材库

## 2. 最关键的一条发现：它们是"技能包"，不是"框架"

这两个项目**都不是**我们原本设想的"要被后端调用的 Python 框架"，而是**给 Agent 读的指令包 + 给 Agent 用的小工具**。

这意味着我们 MRD §8 设计的"技能包"方向是对的，而且现在有了**两个真人验证过的实现**可以直接对标。

**而且 ppt-master 的 README 里明确写着 `harness + model = agent`** —— 说明 D1 对 harness 的理解（模型负责决策、harness 负责执行）与业界实践完全一致。

## 3. 架构级修正：不该有"编排器"

这是这次调研**对我们原设计最重要的一处修正**。

**我原设计的问题**：MRD §9 把 Harness 描述成"内嵌库 + 自研编排层"，隐含了一个 **LangGraph 式的状态机** —— 由 Python 代码来调度 LLM。这是传统做法。

**OpenMontage 的选择（反直觉但更有说服力）**：

> "没有中央编排器。Python 只提供工具和持久化，所有智能都在 Agent 那里。"
>
> 好处：加一个工具＝写一个 Python 类；改流程＝改 YAML 和 Markdown。**不需要动任何核心编排逻辑，因为根本没有核心编排逻辑。**

**为什么这个修正更重要**：我们的三大技能（PPT / 论文 / 漫剧）流程差异极大，且会长出新技能。如果编排逻辑写在 Python 里，每加一个技能就要改主程序 —— 那"技能可插拔"就是假的。

**修正后的职责边界**：

| 层 | 职责 | 用什么写 |
|---|---|---|
| **工具层** | "有什么能力" —— 生图、TTS、渲染、转格式 | Python（注册表自动发现） |
| **技能层** | "每个阶段该怎么做、什么算合格" | Markdown + YAML |
| **智力层** | 决策、取舍、编排 | **Harness 里的模型** |

Harness 内核（OpenHarness）不再是"编排器"，而是**执行环境**：Agent 循环 + 技能按需加载 + 工具注册 + 检查点 + 门禁 + 事件流。**编排是模型读着 YAML 和 Markdown 现做出来的。**

## 4. 可继承资产清单（逐项映射）

以下 9 项是我从两个项目里**直接吸收**的设计。它们解决的都是我们 MRD 里只写了"要做"但没写"怎么做"的部分。

### 4.1 清单格式（manifest）—— 直接采用 OpenMontage 的 schema

它的 `pipeline_defs/*.yaml` 比我 MRD 里的 `manifest.yaml` 草案完善得多。**直接采用**，字段如下：

```yaml
name: comic-drama
version: "1.0"
description: 一句话 → 一集动态漫成品
category: animation
default_checkpoint_policy: guided        # guided / auto / manual

required_skills:                          # 该技能需要加载的 Markdown 技能卡
  - pipelines/comic-drama/script-director
  - pipelines/comic-drama/character-design-director
  - meta/reviewer                         # 自检
  - meta/checkpoint-protocol              # 检查点协议
  - meta/render-runtime-selector          # 渲染引擎选择

orchestration:
  mode: producer                          # 由生产者技能统一指挥
  skill: pipelines/comic-drama/executive-producer
  budget_default_usd: 2.00                # 单次任务预算默认值
  max_revisions_per_stage: 3              # ← 防无限重做
  max_send_backs: 3
  max_wall_time_minutes: 20

compatible_playbooks:                     # 风格剧本（可插拔）
  recommended: [guofeng-ink, flat-anime]
  also_works: [clean-professional]
  custom_allowed: true

stages:
  - name: script
    skill: pipelines/comic-drama/script-director
    required_artifacts_in: [setup_card]
    produces: [script]
    tools_available: []
    checkpoint_required: true
    human_approval_default: true           # ← ★ Gate
    review_focus:                          # 自检要点（给 Critic 看）
      - 每格都有可执行的画面描述，不是情绪词
      - 时长核算与目标秒数一致
    success_criteria:
      - schema 校验通过
      - 角色出场表完整

    sub_stages:                            # ← ★★ 样片子阶段（见 4.7）
      - name: sample
        description: "先出前 3 格 + 分集大纲，5 分钟内给用户看真实效果"
        condition: "approved_concept_exists"
        human_approval_default: true
```

**这套 schema 的三个精髓**：`review_focus`（把"什么算合格"写成给 Critic 的检查项）、`success_criteria`（机器可判）、`human_approval_default`（门禁是数据，不是代码）。

### 4.2 三层知识架构 —— 直接采用

比我 MRD 里的"prompts/ + templates/ + tools/"更清晰，因为它**按"Agent 什么时候需要什么"分层**：

| 层 | 内容 | 回答的问题 | 何时读 |
|---|---|---|---|
| **L1** | `tools/` + `pipeline_defs/` | 有什么能力？流程是什么？ | 开工时 |
| **L2** | `skills/`（含项目约定、质量标准、阶段导演） | 我们**希望**你怎么用它？ | 每个阶段开始 |
| **L3** | `.agents/skills/`（外部技术知识包） | 这个工具**技术原理**是什么？ | 用不熟的工具时按需读 |

**L3 这一层是我原来漏掉的。** 比如"FLUX 的 prompt 怎么写、参数怎么调、什么情况下会失败"，这类供应商知识不该塞进技能包主体（会污染上下文），应该按需加载。**每个工具声明它依赖哪些 L3 技能包。**

### 4.3 检查点协议 —— 直接采用，且有两处我没想到的细节

1. **进阶段先写 `in_progress` 检查点** —— 目的是让用户看到"这一步是活着，不是卡住了"。原话：**"确定性比速度重要"**。这解决长任务的"沉默焦虑"。
2. **门禁强制在检查点层**：一个带门禁的阶段，**没有 `human_approved=True` 就不能写 `completed`**。门禁不是 UI 上的按钮，是落盘时的硬校验。
3. **被取代的检查点归档到 `history/`，门禁转换记录永不销毁** —— 审计链完整。
4. `in_progress` 检查点可以只存部分进度（如"第 3 个场景已完成"），**支持从失败点精确恢复**，而不是整段重跑。

### 4.4 质量门禁 —— 直接采用，比我的设计硬得多

| 门禁 | 机制 | 对我们的价值 |
|---|---|---|
| **反幻灯片门禁** | 6 维「幻灯片风险」评分：重复度、装饰性视觉、运动强度、镜头意图、排版依赖、无依据的电影感 | **直接用于漫剧** —— 防止产出"动起来的 PPT" |
| **交付承诺校验** | 开工时锁定 delivery promise（如"运动主导"），预合成时若 80% 是静图就**拦住渲染** | 承诺在开头定，在结尾验，中间不能偷偷变 |
| **渲染后自审** | `ffprobe` 校验 + 4 个位置抽帧查黑帧/叠加破裂 + 音频电平查静音削波 + 字幕存在性 | **不通过就不交付**。用户永远看不到废品 |
| **源素材检查** | 用户自带素材先 probe（分辨率/编码/声道/时长），**禁止从文件名臆测内容** | 论文的参考文献 PDF、漫剧的用户参考图都适用 |
| **禁止静默降级** | "No silent downgrade" —— 不能偷偷把动态漫降级成静图动画 | 兜底必须显式告知，不是偷偷糊弄 |

### 4.5 预算与配额治理 —— 我原设计只有"成本统计"，这是完整版

```
估价 → 预留 → 执行 → 对账
模式：observe（只记录）/ warn（超额告警）/ cap（硬上限）
默认：单笔超 $0.50 需审批；单任务总额上限 $10
配额：每阶段最多重做 3 次，最多打回 3 次，墙钟上限 20 分钟
```

**`max_revisions_per_stage` / `max_send_backs` 是关键** —— 我的"自校验闭环"设计里，模型自己验收自己回退，**没有边界就会无限循环烧钱**。必须给配额。

### 4.6 七维 Provider 评分 + 决策日志 —— 这就是我 MRD 里的"决策留痕"，但已工程化

每次选工具（生图 / TTS / 音乐 / 视频）都跑 7 维打分：
**任务匹配 30% · 输出质量 20% · 可控性 15% · 可靠性 15% · 成本效率 10% · 延迟 5% · 连续性 5%**

且**选型结果必须带"考虑过的备选 + 置信度 + 理由"写进决策日志**，全流程累积。
→ 这解决了 MRD §7.3 里"决策留痕"的实现问题：**留痕不是额外工作，是选型的副产品。**

### 4.7 样片子阶段（`sample` sub-stage）—— 正是我们的 D9

OpenMontage 的 `character-animation` 流水线里有一个子阶段：

> `sample` — "10-15 秒的角色动画样片，正式生产之前"，`human_approval_default: true`

**这就是你 D9 说的「先满足可用性、先跑最小可信路径」** —— 而且它已经被实现成了一个**结构化的子阶段**：有条件触发（`approved_concept_exists`）、有独立门禁、有独立验收点。

我们不用发明，直接把 `sample` 子阶段作为**技能规范的强制项**。

### 4.8 PPT：SVG → 原生 DrawingML —— vendor ppt-master（MIT）

这一条直接把 MRD §7.1 的"怎么保证给人看"提升了一个档次。原设计只能保证"内容经过取舍"，现在能额外保证：

**产物是原生可编辑的 PowerPoint 对象** —— 拿回去能改字、能挪图、能换色。这才是"给人用的"物质基础（一张图片版 PPT 是死物）。

同时继承它的**两条关键纪律**：

1. **`spec_lock.md` 每页重读** —— 每页生成前必须重读"机器可读的执行契约"，所有颜色/字体/图标/图片只能从这份文件取，**不许凭记忆、不许现场发挥**。
   - 目的：抵抗长文档的**上下文压缩漂移**；并**打破"每页都是卡片网格"的默认**（靠 `page_rhythm: anchor/dense/breathing` 强制节奏变化）
   - **这正是 MRD 里"不罗列、要有判断"最硬的工程手段**：不是靠提示词劝，是靠每页强制对齐契约
2. **逐页串行手写，禁止脚本批量生成** —— 因为跨页视觉一致性依赖"每页都在完整上游上下文里生成"。作者试过脚本批量生成，并在特性分支上废弃了。
3. **一键模式**：八项确认打包成**一次门禁**，一键模式**不提问、自动锁定推荐值**。→ 这就是 D9「3 分钟出草稿」的现成实现，我们照搬。

**一处需要你认可的张力**：ppt-master 的设计哲学是「**AI 是你的设计师，不是完工师**」—— 产出是**设计稿/高质量起点**，最后一公里精装修由人做。这与我们 MRD 里"交付成品"的措辞有出入。
我的判断是**两者不矛盾**：你 D9 说的是"出成品、感觉还不错"，**"还不错"≠"完美"**。所以我建议把验收措辞统一为「**拿到一份愿意继续用下去的成品**」，而不承诺"零修改可用"。

### 4.9 漫剧：直接复用 Remotion / HyperFrames 合成引擎

这是最省力的一块 —— 渲染合成不用自己写。

| 引擎 | 技术 | 适合 | 关键能力 |
|---|---|---|---|
| **Remotion** | React | 数据驱动解说、图片动画 | 弹簧动画场景、文字卡、数据卡、图表、**TikTok 式逐字字幕**、Ken Burns 运镜 |
| **HyperFrames** | HTML/CSS/GSAP | 动效密集、**绑定角色动画** | 动态排版、产品宣传、**SVG 角色绑定动画** |

**实测成本参考**（OpenMontage 官方示例）：
> 12 张 AI 图 + 交叉淡入淡出 + 电影感运镜 + 粒子叠加 + 环境乐 → **$0.15/条，零视频生成 API**

这个数字对"3 分钟出草稿"的北极星指标是极其关键的支撑。

## 5. 漫剧（动态漫）的两条技术路线 —— 需要你选

调研后我发现动态漫有**两条都能落地**的路，而且 OpenMontage **两条都实现了**：

### 路线甲：AI 生图分镜 + Remotion 运镜（视觉丰富）

```
剧本 → 角色定妆卡（一致性锚点） → 逐格 AI 生图 → 每格做运镜（zoom/pan/Ken Burns）
     → 交叉淡入淡出 + 粒子叠加 → 配音 + BGM → Remotion 合成 → mp4
```

- ✅ 视觉最接近"漫剧"，画面丰富
- ✅ 成本极低（$0.15/条）、零视频生成 API
- ⚠️ **跨格角色一致性是最大难点**（靠定妆卡 + 参考图 + 风格种子约束缓解，无法根治）
- ⚠️ 本质是"静图 + 运镜"，有被反幻灯片门禁拦住的风险 → 必须靠运镜强度和粒子/视差来"真动起来"

### 路线乙：SVG 绑定角色动画（一致性完美）

```
剧本 → 角色规格 → SVG 骨架绑定（部件/枢轴/图层） → 姿态库 → 动作时间轴
     → HyperFrames 浏览器渲染 → mp4
```

- ✅ **角色一致性完美**（同一个绑定，怎么动都不会变脸）
- ✅ 完全免费、可离线、可复现（确定性渲染）
- ✅ 能表达"表演"（停顿、预备、跟随）
- ⚠️ 画风是**矢量卡通**，不是漫画质感
- ⚠️ 需要建骨架和姿态库，前期投入大

### 我的建议

**主做路线甲，把路线乙作为"一致性兜底/特殊风格"。**

理由：路线甲能最快满足 D9（3 分钟出草稿、视觉冲击强、成本忽略不计）；路线乙虽然一致性完美，但"矢量卡通"风格对"漫剧"这个品类的用户预期是有落差的，且前期投入大，不适合做第一款。

## 6. 许可证 —— 最硬的约束

### OpenMontage = AGPL-3.0（强 copyleft）

- **网络使用即触发传染**：只要用户能通过网络与程序交互，就必须向用户提供修改后的完整源码
- 仓库**没有双重授权、没有商业例外**
- 影响矩阵：

| 使用方式 | AGPL 约束 |
|---|---|
| 个人本地使用 | 无约束 ✅ |
| 内部工具（不对外服务） | 灰色地带，需法务确认 ⚠️ |
| **SaaS / 对外服务** | **必须开源所有修改** 🔴 |
| **闭源商业产品集成** | **违规** 🔴 |

**我们的处置：只借鉴架构与清单设计，用自研代码重新实现。**
完全可行 —— 因为我们要的就是"它的架构思想"（无编排器、三层知识、检查点协议、质量门禁、配额治理），这些是**方法论，不受版权保护**。真正要重写的是 `tools/` 下的 Python 实现和 500+ 个技能 Markdown —— 而我们的技能是 PPT/论文/漫剧，本来就要自己写。

**备选**：如果后续想省事，可以联系作者谈商用授权。

### ppt-master = MIT（可直接用）

- ✅ 可自由使用、修改、闭源商用、再分发
- ⚠️ **唯一坑**：可选依赖 `PyMuPDF` 是 **AGPL-3.0**（仅 `pdf_to_md.py` 导入，只用于转换 PDF 源）
  - 对策：我们的 PDF 解析改用别的方案（`pypdf` / `pdfplumber`，都是 BSD/MIT），或干脆不转 PDF
  - 若要再分发打包了 PyMuPDF 的产物，需先核对 AGPL 条款

## 7. 本机环境实测（能不能落地）

| 项 | 实测结果 | 影响 |
|---|---|---|
| **GitHub 直连** | ❌ 不通（`github.com` / `raw.githubusercontent.com` / `jsdelivr` 全部超时或 502） | 不能用 `git clone` 直接拉源码 |
| **ghproxy.net 镜像** | ✅ 通 | 已验证可拉取 README / SKILL.md / manifest / 依赖清单；源码包可拉但较慢 |
| **gitee.com** | ✅ 通 | 备选镜像 |
| **PyPI** | ✅ 通 | 所有 Python 依赖可装 |
| **npm 官方源** | ❌ 不通 | Remotion 装不了 |
| **registry.npmmirror.com** | ✅ 通 | **须把 npm 源切到 npmmirror** |
| **Docker / Postgres / brew** | ❌ 全无 | 保持 D4 决策：开发期 SQLite |

**结论**：可以落地，但有两处必须配置：① 拉源码走 ghproxy 镜像；② npm 源切 npmmirror。这两条我已写进 MRD §13。

## 9. 这次调研带来的净收益
