## 0. 产品定位与价值命题

### 0.1 一句话定位

一个面向"**长周期、多步骤、有实物产物**"的 AI 工作台。用户选择一类任务技能（首发三类：**做 PPT / 写论文 / 做漫剧**），系统以 **Harness 执行内核**驱动：把一句模糊需求拆成可确认、可暂停、可恢复、可交付的任务流水线，最终产出**能直接拿去用的文件**（pptx / docx / mp4）。

**产品名**：**Longspan**（中文可叫「长跑」）✅ 已定（决策 D7）

### 0.2 核心命题：价值不在「生成」，在「约束与留痕」

**生成能力正在以季度为单位贬值。** 今天需要接三个 API、调两天提示词工程才能达到的画面，半年后是某个平台的默认能力。任何建立在"我会调模型"之上的护城河，都会随模型迭代被抹平。

而下面三样东西不会随模型贬值 —— 因为它们解决的不是"模型能不能生成"，而是"生成结果能不能被信任、被复现、被交付"：

| 不贬值的资产 | 本产品的具体形态 | 平台为什么不给 |
| --- | --- | --- |
| **约束** | 技能 manifest 里的阶段顺序、验收标准、镜头预算、一致性硬校验、单格单动作 | 平台只给"一键"，不给"按我的规范来" |
| **留痕** | `decision` 记录、降级上报、`draft_gaps`、格级重绘的幂等记账、回退链说明 | 平台不解释"这一格为什么长这样" |
| **编排** | HITL 关卡、断点续跑、局部重跑、换模型 / 换供应商 / 换画风 | 平台锁定自家模型与自家流程 |

> **一句话：生成能力在下沉，判断权在上浮。本产品只做上浮的那一半。**

这条命题一旦成立，就直接决定了需求优先级：**凡是"换个更强的模型就能解决"的需求，优先级自动降一级；凡是"接十个模型也解决不了、必须靠规范和流程"的需求，优先级提一级。**

### 0.3 三层价值与我们的取舍

| 层 | 内容 | 是否投入 | 判据 |
| --- | --- | --- | --- |
| 能力层（能不能做出来） | 接生图 / 配音 / 视频 / 渲染 | **够用即接、可换即走** | 不为某一个模型写死架构；能力落后就在 `media/` 里换实现，不动流程 |
| 约束层（结果可不可信） | 阶段验收、硬校验、镜头预算、风格锚、演出规范 | **重投入（主战场）** | 一致性 / 风格 / 时长这类"结果质量"，优先用**规范**解决而不是等模型 |
| 资产层（下次能不能复用） | 技能包、产物契约、指标记账、可分享的流程 | **重投入** | 换题材只改 manifest 词条 = 合格；每次都要改代码 = 还不是产线 |

**取舍结论：能力层做"接入"，约束层和资产层做"产品"。**

### 0.4 明确不做什么

以下四条是**边界**，不是待办。写在这里是为了让每次讨论有刹车：

1. **不做"一句话出爆款"的全自动黑盒** —— 与附录 A 一致。长任务里 20% 的关键判断决定 80% 的质量，这些必须留给人拍板。
2. **不与平台比模型质量、比生成速度** —— 即梦 / 可灵 / 剪映的模型是自己训的，比不过也不该比。我们比的是"同一条规范下能不能稳定复现"。
3. **不做单点工具**（滤镜、去水印、一次性换脸） —— 单点工具的价值全在能力层，正是贬值最快的部分。
4. **不追 LoRA / 自训模型** —— 除非一致性成为唯一瓶颈，且约束层（演出规范）+ 素材层（参考图通道）都已用尽。训练是最后一张牌，不是第一张。

### 0.5 三种定位的取舍记录（2026-10-22 复盘）

对"这个项目到底有没有价值"的回答，必须先选定一种定位。三种候选的真实价值差一个量级：

| 定位 | 形态 | 护城河 | 结论 |
| --- | --- | --- | --- |
| **A 全自动出片工具** | 一句话 → 成片，人不介入 | **薄**，且随时间贬值。你在应用层做的任何一致性 trick，下一版模型可能直接内置 | ❌ 不做 |
| **B 编排内核** | harness + 技能 manifest + 关卡 + 决策留痕 | **厚**，可迁移。平台不给你解释链、不给你插人审、不给你换供应商 | ✅ 主定位 |
| **C 半自动辅助** | 批量出素材 + 分段人审 + 人做最终剪辑 | **中**，最快见效，最不容易被吞（价值在批量与对照，不在"一键"） | ✅ 交付形态 |

**选择：以 B 为主定位，以 C 为默认交付形态，不做 A。**

反面也要写清楚：如果目标只是"发短剧账号涨粉"，本项目的投入产出比很差 —— 买平台会员 + 手工剪更快。**它值得做的前提是：真的需要"一条能反复跑、能换题材、能给第二个人用的产线"，而不是"这一支片子"。**

### 0.6 判定线：什么时候该继续，什么时候该收手

不靠感觉，靠三个可计量指标（连续两集不达标 → 停止加功能，回到规范层）：

| # | 指标 | 口径 | 及格线 |
| --- | --- | --- | --- |
| 1 | **返工率** | 需要重做的格数 ÷ 总格数（含人工判定返工 + 硬校验失败重做） | ≤ 1/12 |
| 2 | **换题材成本** | 新开一集时"改 manifest 词条"与"改代码"的比例 | 100% 改词条，0 行代码 |
| 3 | **TTFV 里"等人"占比** | 精修耗时中人工关卡等待时长 ÷ 总时长 | ≤ 30%（等人的时间不能算自动化） |

> 这三个指标同时也是**诚实性指标**：只要有一项不达标，说明自动化收益正在被返工或人力悄悄吃掉，此时加功能只会让账更难看。

## 1. 背景与问题

当前用 AI 做一件"大活"时，用户普遍遇到五个硬伤：

| #  | 痛点            | 现状                              | 本产品解法                                 |
| -- | ------------- | ------------------------------- | ------------------------------------- |
| P1 | **一次输出，无法迭代** | 一句话吐出 20 页 PPT，方向错了只能重开         | 拆成阶段，每个阶段有产物、有验收，可**局部重跑**            |
| P2 | **中途无法干预**    | 跑到一半发现跑偏，只能打断重来                 | **HITL 人工关卡**：大纲/分镜/选题等关键节点强制暂停确认     |
| P3 | **上下文爆炸**     | 论文写到第 5 章，前面内容已被遗忘，术语前后不一致      | **分层记忆 + 阶段产物落盘**，每阶段读盘续写而非靠上下文硬记     |
| P4 | **断了要重来**     | 网络抖动、超时、关页面 → 几小时工作归零           | **Checkpoint 断点续跑**，Run 状态持久化，可从中断处恢复 |
| P5 | **产物不可交付**    | 拿到一堆 Markdown，还要自己排版成 pptx/docx | 原生生成**交付级文件**，并支持版本管理与导出              |

> 核心判断：**「能跑完一个多小时的长任务」不是模型能力问题，而是工程编排问题。** 这正好是 Harness 框架要解决的事。

## 3. 核心概念定义（术语表）

这套概念是整个系统的骨架，前后端、技能包、数据库都围绕它们建。

| 概念   | 英文               | 定义                                                         |
| ---- | ---------------- | ---------------------------------------------------------- |
| 工作区  | **Workspace**    | 一次长任务的容器。含会话、文件、产物、记忆。可理解为一个"项目文件夹"                        |
| 任务技能 | **Skill**        | 可插拔的能力包（`SKILL.md` + manifest + 提示词 + 模板 + 工具）。决定"这类任务怎么做" |
| 运行实例 | **Run**          | 某个 Skill 在工作区里的一次执行。有状态机、有成本、有日志                           |
| 阶段   | **Step / Stage** | Run 被切成的有序单元。每个阶段有目标、输入、产物、验收标准                            |
| 关卡   | **Gate**         | 需要人工确认才放行的阶段出口（例如"大纲确认"）。不确认就挂起                            |
| 产物   | **Artifact**     | 阶段产出的文件：md / json / pptx / docx / png / mp3 / mp4          |
| 检查点  | **Checkpoint**   | 阶段完成时落盘的状态快照，用于断点续跑与分叉重跑                                   |
| 事件流  | **Event Stream** | 执行过程中所有事件的统一有序流（思考、工具调用、产物、错误），SSE 推给前端                    |
| 轨迹   | **Trajectory**   | Run 的完整历史：每一步的输入输出、模型、token、耗时。可回放、可调试                     |

## 5. 核心用户旅程（关键：HITL 关卡）

```
① 建任务          选技能卡片（PPT / 论文 / 漫剧）+ 填 Brief（结构化表单 + 自由描述）
      ↓
② 澄清 Clarify    Agent 反问 3~5 个关键问题（受众？页数？风格？引用规范？）
      ↓
③ 出计划 Plan     生成「任务计划书」：阶段列表 + 每阶段目标/产物/工具/预计耗时/成本预估
      ↓
④ 确认计划 ★Gate  用户可 增/删/改/换序 阶段，确认后才开跑     ← 强关卡
      ↓
⑤ 执行 Execute    按阶段依次跑，SSE 实时推事件流，产物逐步落盘
      ↓
⑥ 关卡确认 ★Gate  中途关键节点暂停（大纲 / 选题 / 分镜 / 角色形象）  ← 强关卡
      ↓
⑦ 产出 Deliver    产物出现在右侧，可预览 / 下载
      ↓
⑧ 迭代 Iterate    "第 3 页再补一个图表" → 只重跑受影响的阶段
      ↓
⑨ 导出归档        打包下载 / 归档
```

**设计要点**：Step ④ 和 ⑥ 是整个产品的体验分水岭。宁可多停两次，也不要跑完两小时发现方向错了。

### 5.1 首次体验路径（Time to First Value）★ 决策 D9

需求方原话：

> 「先满足可用性，再批量。适合小白用户试一下就出效果、出成品，他感觉还不错。然后再考虑留存。」

这句话定义了本产品的**北极星指标**：

> **北极星指标 = 一个新用户从打开产品到拿到第一份「他愿意继续用下去」的成品，需要多久。**

不是"生成了多少文件"，不是"功能覆盖率"，而是：**第一次用，几分钟内，拿到一个他看了觉得"还行"的东西。**  
没有这个"还行"，后面所有功能都没有用户。

#### 5.1.1 双通道设计（核心机制）

| 通道      | 名称   | 触发方式      | 耗时目标       | 产出            | 目的                        |
| ------- | ---- | --------- | ---------- | ------------- | ------------------------- |
| **快通道** | 秒出草稿 | 默认路径      | **≤ 3 分钟** | 一份「可用但不精细」的成品 | 3 分钟内让用户看到**真实产物**，建立信任   |
| **慢通道** | 精修打磨 | 用户点「继续优化」 | 20~60 分钟   | 完整质量成品        | 走完整流水线 + Critic 评审 + 全部关卡 |

**关键判断**：只有快通道跑通、并且有人愿意点「继续优化」，慢通道才有意义。  
所以 **MVP 的第一优先级是快通道**，而不是功能覆盖度。

#### 5.1.2 快通道怎么做到 ≤ 3 分钟

| 手段         | 具体做法                                               |
| ---------- | -------------------------------------------------- |
| **零输入也能跑** | 所有 inputs 都有合理默认值；用户只填一句话、甚至什么都不填（用示例）就能启动         |
| **砍关卡**    | 快通道只保留 **1 个**关卡（PPT 是大纲秒确认 / 漫剧是剧本确认），其余决策全自动     |
| **并行化**    | 资料检索与叙事定调并行；分镜生图分批并行                               |
| **模型降级**   | 快通道用更快的模型；Critic 只跑一轮，不做多轮打回                       |
| **尽早交付**   | 不等全部完成 —— PPT 在第 3 阶段就给「可翻看的大纲稿」，漫剧在第 2 阶段就给「首格样图」 |

#### 5.1.3 降低首屏门槛

- **示例任务一键试用**：「季度业绩汇报」「毕业论文开题」「60 秒悬疑漫剧」——点一下直接开跑，不用填表单
- **表单全部预填推荐值**：每个字段都有默认值 + 示例文案
- **不做必填拦截**：留空即用默认值，并在计划里明确告知"我替你填了什么"

#### 5.1.4 体验预期管理

- 快通道产出**明确标注为「草稿」**，并附「还能怎么变好」清单（3~5 条可一键执行的优化项）
- **不假装完美** —— 让用户知道这是起点，不是终点。这一条同时保护了慢通道的价值感

### 5.2 排期原则：可用性 → 留存 → 规模化

| 阶段         | 目标         | 判据                  | 明确不做什么                |
| ---------- | ---------- | ------------------- | --------------------- |
| **P0 可用性** | 第一次用就出成品   | 新用户 3 分钟内拿到草稿，且愿意继续 | 不做协作、不做批量、不做技能市场、不做分享 |
| **P1 留存**  | 用户愿意回来用第二次 | 复访率、「继续优化」转化率       | 才考虑批量、模板、历史管理         |
| **P2 规模化** | 批量与生态      | 批量任务、第三方技能          | —                     |

> **优先级纪律**：凡是不能提升「第一次就出成品」的功能，一律往后排。  
> §6.1 中 F-13~F-22 的多数条目属于 P1/P2，不要提前做。**做减法比做加法重要。**

## 7. 三大技能规格

> 每个技能 = 一条**阶段流水线**。以下是各技能的阶段设计（这是本 MRD 最需要你确认的部分）。

### 7.1 技能 A：PPT 生成（`ppt-deck`）

> **产品定义（很重要）**：我们生产的是**给人讲的演示文稿**，不是"把资料塞进模板的容器"。  
> 一份好 PPT 的判据只有一条：**听众看完记住了什么**，而不是"覆盖了多少信息"。  
> AI 做 PPT 的默认失败模式是"能放的都放"；人类做 PPT 的核心动作恰恰是**删**。所以整套机制要逼模型显式回答"**为什么删**"。

| 阶段 | 名称       | 动作                                     | 产物             | Gate       |
| -- | -------- | -------------------------------------- | -------------- | ---------- |
| A1 | 需求澄清     | 问：主题/受众/场景/时长/页数/语言/风格                 | 需求卡            | —          |
| A2 | 资料准备     | 联网检索 + 上传资料解析 → 原始素材池                  | 素材库            | —          |
| A3 | **叙事定调** | 提炼 deck 核心主张（一句话，含判断）+ 3~5 条 MECE 支撑论点 | `thesis.md`    | **★ 主张确认** |
| A4 | 页面规划     | 论点 → 页面分配（一页一论点）+ **取舍清单**             | `outline.md`   | **★ 大纲确认** |
| A5 | 逐页撰写     | 断言式标题 + ≤3 支撑点 + **讲者备注**              | `content.json` | —          |
| A6 | 视觉设计     | 按"信息-版式决策表"选版式与图表                      | 版式方案           | 可选         |
| A7 | **评审自检** | Critic 逐页打分，不合格页打回重做                   | `review.md`    | —          |
| A8 | 文件生成     | 渲染成 pptx（复用 `tencent-pptx` 能力）         | `deck.pptx`    | —          |
| A9 | 终检导出     | 溢出、错别字、字体嵌入、导出 pdf                     | `deck.pdf`     | —          |

#### 7.1.1 六条硬规则：保证"给人看"而不是"信息罗列"

| #      | 规则                   | 具体约束                                                  | 机器可校验      |
| ------ | -------------------- | ----------------------------------------------------- | ---------- |
| **R1** | **先有主张，才有页面**        | 必须先产出 deck 级核心主张（一句话、含明确判断），未产出不允许进入页面规划              | 断言句检测      |
| **R2** | **标题必须是断言句，不是名词短语**  | 每页标题 = 主语 + 判断（+ 数字）。❌「市场情况」✅「华东增速放缓至 8%，低于全国均值」      | 规则 + 模型双校验 |
| **R3** | **一页一论点**            | 每页只承载 1 个论点、≤3 个支撑点、1 个视觉主体；正文 ≤ 60 字                 | 字数/条目数硬校验  |
| **R4** | **必须做取舍，且留痕**        | 素材池 → 候选论点 → 入选页面 三级过滤；**被删内容与删除理由必须显式记录**（Kill List） | 结构校验       |
| **R5** | **页面文字 ≠ 全部信息**      | 细节下沉到讲者备注与附录；备注信息量应 ≥ 页面文字量                           | 长度比对       |
| **R6** | **版式由信息类型决定，不由模板决定** | 见 7.1.3 决策表                                           | 类型映射       |

#### 7.1.2 核心机制：素材 → 论点 → 页面 的三级过滤

这是"关键信息提取 + 自己的判断"的落地方式。**AI 的判断不体现在"选了什么"，而体现在"为什么删"** —— 所以产品必须逼它显式回答"为什么删"。

| 层级              | 内容                       | 占比   | 谁决定                  |
| --------------- | ------------------------ | ---- | -------------------- |
| L1 素材池          | 检索/上传得到的全部原始信息           | 100% | 工具采集                 |
| L2 候选论点         | 从素材中提炼、可支撑核心主张的论断（带证据出处） | ~30% | 模型提炼 + 打分            |
| L3 入选页面         | 最终进入 PPT 的页面             | ~20% | 模型决策 + **用户在大纲关卡确认** |
| ✂ **Kill List** | 被剔除的素材/论点 + **剔除理由**     | 显式记录 | 模型，用户可查看、可捞回         |

**Kill List 的剔除理由必须归入以下五类之一**（逼模型做真判断，而不是含糊其辞）：

| 理由      | 含义               |
| ------- | ---------------- |
| `与主张无关` | 不支撑核心主张          |
| `弱于同类`  | 有更好的一条替代它        |
| `听众已知`  | 对这批听众是常识，不值得占用页面 |
| `细节过深`  | 下沉到讲者备注或附录       |
| `证据不足`  | 数据不可靠或没有出处       |

> 用户可在工作台查看完整 Kill List，随时"捞回"某条。**这既给了模型判断权，又没让用户失去控制权。**

#### 7.1.3 版式决策表（信息类型 → 页面形态）

| 信息特征              | 版面形态                   | 禁止          |
| ----------------- | ---------------------- | ----------- |
| 单一强结论             | 大字句 + 一句话              | 堆装饰元素       |
| 2~5 点并列           | 分栏卡片                   | 写成大段文字      |
| 有时间序              | 时间轴                    | 用项目符号假装时间轴  |
| 有对比数据             | 图表（柱/折/散）              | 用文字描述数字     |
| 有流程/因果            | 流程/因果图                 | 流水账段落       |
| 有明显对照项            | 左右对照                   | 混在一起讲       |
| **以上都不符合，只是"罗列"** | **强制回到 L2 重做归类-排序-取舍** | **直接生成列表页** |

最后一行是重点：**当模型想输出一个"什么都有一点点"的页面时，这是它偷懒的信号，系统要强制它回去重新做判断。**

#### 7.1.4 评审自检清单（Critic Agent 逐页打分）

每页必须通过 5 问，任一不过 → 打回该页重做（最多 2 次，仍不过则标记并提示用户）：

1. **这页的 takeaway 是什么？能用一句话说出来吗？** —— 说不出 = 这页没有论点
2. **删掉这页，整个故事还成立吗？** —— 成立 = 冗余，应该删
3. **标题是断言还是标签？** —— 标签 = 不合格
4. **每个数字都有出处吗？** —— 没有 = 不合格
5. **听众看完最可能问的问题，这页回答了吗？** —— 没答 = 需补内容，或这页放错了位置

整份 deck 层面再问 3 问：

1. 主张是否经得起反问？有没有明显的反例没处理？
2. 章节之间是**递进**关系，还是并列堆叠？
3. 有没有某一页的信息密度显著高于其他页？为什么？

#### 7.1.5 判断过程必须可见（工作台要显示什么）

模型不能只在暗处做判断，产品要把判断摊开给用户看：

- **主张卡**：deck 的一句话核心主张 + 支撑它的 3~5 条论点
- **取舍面板**：三级漏斗数量对比（例：采集 148 条 → 提炼 41 条 → 入册 14 页，剔除 27 条）
- **Kill List**：每条被删内容 + 理由标签 + 一键捞回
- **每页的"为什么"**：标题为什么这么写、为什么选这个版式、这页服务哪条论点
- **评审报告**：Critic 的打分与打回记录


> **一句话总结：给人看的 PPT = 断言式表达 + 显式取舍 + 版式匹配 + 独立评审。四者缺一，就会退化成信息罗列。**

### 7.3 技能 C：漫剧制作（`comic-drama`）

> ✅ **已确认（决策 D5）**：本技能做 **动态漫 / 有声漫画** —— 漫画分镜图 + 配音 + 镜头运动 + 字幕 → 竖屏短视频。  
> **不做** AI 真人短剧（真人感视频片段 + 剪辑）。后者未来可作为独立技能扩展，不进入本期范围。

> **产品定义（很重要）**：用户只给**约束**，不给**步骤**。  
> 用户说：「做一个 60 秒的竖屏悬疑漫剧，主角是个送外卖的女生。」  
> 系统要自己完成：定基调 → 写剧本 → 定角色 → 拆分镜 → 生图 → 配音 → 合成 → 成片。

| 阶段 | 名称       | 动作                           | 产物            | Gate       |
| -- | -------- | ---------------------------- | ------------- | ---------- |
| C1 | 约束解析     | 把一句话拆成 硬约束 / 软偏好 / 自由区       | 设定卡           | —          |
| C2 | **生产规格** | 反推出可执行规格：分镜数、节奏表、工具链、预算      | `spec.json`   | 轻确认        |
| C3 | 剧本       | Logline → 人物小传 → 分集大纲 → 分镜脚本 | `script.md`   | **★ 剧本确认** |
| C4 | 角色设计     | 角色卡（外貌/服装/性格）+ 定妆图，锁定一致性锚点   | `characters/` | **★ 形象确认** |
| C5 | 分镜绘制     | 逐格生图，带角色参考图 + 风格种子约束         | `panels/`     | 可抽检        |
| C6 | 配音与音效    | TTS 台词 + BGM + 音效            | `audio/`      | —          |
| C7 | 合成       | 分镜运动、字幕、时间轴对齐 → 成片           | `ep01.mp4`    | —          |

#### 7.3.1 机制一：约束分层 —— 用户给边界，模型填空

「一句话生成」失败的根本原因，是系统分不清**哪些是用户的意志、哪些是自己的判断**。所以第一步必须把输入显式拆成三层：

| 层级           | 内容                        | 来源         | 出现分歧时             |
| ------------ | ------------------------- | ---------- | ----------------- |
| **硬约束 Hard** | 时长、集数、画幅、平台、分级、预算上限、品牌规范  | 用户明确说的     | 必须满足；不满足就**停下来问** |
| **软偏好 Soft** | 画风、色调、节奏、情绪基调             | 用户暗示或选择的   | 尽量满足；可协商，偏离需告知    |
| **自由区 Free** | 分镜数量、每格构图、运镜方式、转场、音效、台词措辞 | **模型全权决定** | 模型说了算，但必须**留痕**   |

**产品必须显式展示"我替你做了哪些决定"**（见 7.3.4）。用户不写步骤，但要看得到步骤，并且能推翻。

#### 7.3.2 机制二：骨架由技能定，细节由模型填 ★核心

这是"稳定"与"聪明"的平衡点，也是最容易做错的地方：

- ❌ **错误做法 A**：给模型 20 个工具，让它从零自由编排 → 结果不稳定，每次跑法都不一样，出错无法复现、无法优化。
- ❌ **错误做法 B**：把流程写死成固定模板 → 换个题材就僵化，用户感觉在填表。
- ✅ **正确做法**：**技能 manifest 定义 DAG 骨架（阶段与依赖），模型在每个阶段内部自主决策。**

```
技能定义（稳定、可复现）        模型决策（灵活、自适应）
─────────────────────────     ──────────────────────────────────
C1 → C2 → C3 → C4 → C5 → C6 → C7
                                ├─ 本阶段用哪个工具（白名单内自主选）
                                ├─ 参数怎么定（如 60秒÷5秒/格 = 12 格分镜）
                                ├─ 要不要重试 / 换方案（生图不满 → 换 seed / 换模型）
                                └─ 是否触发自检、是否回退重做本步
```

用一句话概括：**Skill-defined skeleton + model-driven execution**（技能定骨架，模型跑细节）。

#### 7.3.3 机制三：工具契约必须"模型友好"

模型能不能自主调度，取决于工具的说明书写得好不好。每个工具在技能包里必须声明：

| 字段              | 作用              | 例子                                           |
| --------------- | --------------- | -------------------------------------------- |
| `when_to_use`   | 什么时候该用它（自然语言）   | 「需要生成单格分镜画面，且已有角色参考图时」                       |
| `inputs`        | 输入 schema + 约束  | `{prompt, ref_image?, seed?, aspect:"9:16"}` |
| `outputs`       | 产出与格式           | `png 1080×1920`                              |
| `cost`          | 成本与耗时量级         | `约 0.3 元 / 15 秒`                             |
| `failure_modes` | 失败表现 + **替代方案** | 「内容审核拒绝 → 改写提示词重试；连续 3 次失败 → 切换备用模型」         |
| `examples`      | 1~2 个真实调用示例     | 让模型学会怎么调                                     |

> **关键在 `failure_modes` 里的"替代方案"** —— 这是自主性的真正来源。没有它，模型遇到失败只能干等或把错误丢给用户。

#### 7.3.4 机制四：决策留痕 —— 用户只提约束，但不失去控制

模型每做一个自主决定，都写入事件流并结构化记录：

| 时间    | 决定                   | 依据                  | 可推翻 |
| ----- | -------------------- | ------------------- | --- |
| 00:12 | 切分为 12 格分镜，每格约 5 秒   | 硬约束"60 秒" + 悬疑需留白节奏 | ✅   |
| 00:31 | 主角外观锁定 seed=48213    | 保证跨格一致性             | ✅   |
| 01:05 | 第 7 格改用冷色调           | 剧情转折点，情绪需要          | ✅   |
| 02:40 | 第 3 格生图失败 2 次，切换备用模型 | 工具契约的 failure_modes | —   |

**"可推翻"是关键**：用户不需要事前写步骤，但事后能改任何一步，系统从该步重跑下游。

#### 7.3.5 机制五：自校验闭环（模型自己发现问题，不丢给用户）

每个阶段模型必须自己验收，不合格自己回退重做（有重试上限）：

| 阶段  | 自校验项                | 不合格怎么办    |
| --- | ------------------- | --------- |
| 剧本  | 分镜是否覆盖全部关键情节点？      | 补缺失情节     |
| 角色  | 跨格角色是否一致（脸型/发型/服装）？ | 重绘不一致的格子  |
| 分镜图 | 画面是否符合剧本描述？有无穿帮？    | 重绘该格      |
| 时长  | 总时长是否落在硬约束内（±10%）？  | 调整格数或每格时长 |
| 音画  | 字幕与配音是否对齐？          | 重校时间轴     |

> 原则：**能在系统内解决的问题，不要变成用户的问题。** 只有当自校验连续失败达到上限时，才升级为"请求人工介入"。

#### 7.3.6 机制六：先跑最小可信路径

一句话输入最容易"模型想太多"—— 一口气生成 20 集、跑 3 小时，结果画风不对。

**策略**：先只做 **1 集 + 前 3 格**，让用户看到真实效果，确认后再批量扩展。

- 好处：**5 分钟拿到真实反馈**，而不是 3 小时后拿到废品
- 成本：几乎为零
- 实现：C5 阶段支持"抽样预览模式"

#### 7.3.7 兜底策略

| 风险                   | 兜底                        |
| -------------------- | ------------------------- |
| 模型步骤失控（陷入循环）         | 步数上限 + 成本上限，超限则降级为简化方案并告知 |
| 硬约束无法满足（如 60 秒装不下剧本） | **停下来问，不擅自改约束**           |
| 一致性始终不达标             | 提示用户上传角色参考图 / 主动降低风格复杂度   |
| 内容审核拦截               | 自动改写提示词；重试到上限后请求用户介入      |

> **最大技术风险**：**跨格角色一致性**。对策见 §14 风险 R3。

### 7.4 这两个问题的共性：判断权与自由度的分配

你提的两点，本质是同一个问题的两面：

|       | PPT 技能                                 | 漫剧技能                             |
| ----- | -------------------------------------- | -------------------------------- |
| 用户给什么 | 主题 + 受众 + 场景                           | 一句话约束                            |
| 真正的难点 | 信息太多 → 需要**取舍判断**                      | 步骤太多 → 需要**自主调度**                |
| 典型失败  | 退化为信息罗列                                | 退化为不可控的随机输出                      |
| 解法    | 强制三级过滤 + Kill List + 断言式表达 + Critic 评审 | 约束分层 + 骨架定流程 + 工具契约 + 决策留痕 + 自校验 |

**提炼出的三条通用原则**（适用于所有技能，包括后续新增的）：

1. **判断必须显式化** —— 模型做的每个取舍/决定，都要有记录、有理由、可见、可推翻。**看不见的判断 = 不可信的判断。**
2. **结构由技能定，细节由模型定** —— 流程骨架写进 `manifest.yaml`（保证稳定可复现），阶段内的选择交给模型（保证灵活不僵化）。
3. **能在系统内解决的，不要变成用户的问题** —— 自校验、自动重试、自动降级；只有兜不住时才升级为人工介入。
4. **能用规范解决的，不要指望模型自觉**（v1.4 新增，定位的直接推论）—— 凡是"模型应该记住"的东西（角色长相、画风、镜头语法、时长配比），都必须在流程里有**显式声明 + 机器校验**。写进提示词 = 建议，写进 manifest 校验 = 契约。一致性不是模型的承诺，是流程的承诺。

## 8. 技能（Skill）规范——可插拔的关键

这是"后端用 Harness 通过加载技能实现不同长任务"的落地点。技能包就是**一个目录**：

```
skills/ppt-deck/
├── SKILL.md            # 必需。frontmatter + 自然语言流程说明（兼容 Anthropic Skills 格式）
├── manifest.yaml       # 必需。机器可读：阶段定义、Gate、工具依赖、验收、产出类型
├── prompts/            # 各阶段提示词模板（含变量占位）
│   ├── clarify.md
│   ├── outline.md
│   └── ...
├── templates/          # 模板资产：pptx 母版、论文样式、画风参考
├── tools/              # 该技能专属工具（Python 脚本 / MCP 声明）
└── fixtures/           # 测试用例与期望产物（技能自检用）
```

**`manifest.yaml` 关键字段**（草案）：

```yaml
id: ppt-deck
name: 制作演示文稿
version: 1.0.0
description: 从主题到可交付 pptx
inputs:                      # 建任务时采集
  - key: topic
    label: 主题
    type: text
    required: true
  - key: pages
    label: 页数
    type: number
    default: 15
stages:
  - id: clarify
    name: 需求澄清
    tools: [ask_user]
  - id: outline
    name: 大纲生成
    produces: [outline.md]
    gate: true               # ← 该阶段出口需要人工确认
    accept: "覆盖全部要求要点，每页有明确结论"
  - id: render
    name: 生成 pptx
    tools: [pptx_render]
    produces: [deck.pptx]
artifacts: [pptx, pdf, md]
model_hints:
  long_context: true         # 提示路由到长上下文模型
max_runtime_minutes: 90
```

**技能加载与运行契约**（Harness 侧）：

1. 启动时扫描 `skills/` → 解析 manifest → 注册到技能表；
2. 创建 Run 时按 `skill_id` 装载：注入 `SKILL.md` 到系统提示 + 绑定该技能的工具白名单；
3. 每阶段：取 prompt 模板 → 填变量 → 走 Agent 循环 → 校验 `accept` → 落盘产物 → 打 Checkpoint；
4. 技能可以**热插拔**：新增目录即新增能力，不动主程序代码。

## 9. 系统架构

**分层**：前端 → API 层 → Harness 执行内核 → 技能层 → 能力层（模型/工具/沙箱）→ 存储层。

**关键决策一**：Harness **以内嵌库方式**被后端调用（而非跑 CLI 子进程），这样才有：

- 任务状态可控（暂停/恢复/取消）
- 事件流可直接接 SSE 推给前端
- 单进程内多 Run 并发调度
- 产物与 Checkpoint 直接落库

**关键决策二（v1.2 架构修正）：Harness 是执行环境，不是编排器。**

原设计里写的「OpenHarness 内核 + **自研编排层**」，隐含了一个 LangGraph 式状态机（用 Python 调度 LLM）——**这是错的**，必须改掉。

> **没有中央编排器。** Python 只提供工具与持久化，所有智能都在模型那一侧。
> 加一个工具 = 写一个 Python 类；改流程 = 改 YAML 和 Markdown，**因为根本没有核心编排逻辑可以改**。

**为什么这个修正对我们的场景是致命的必要**：我们规划了 PPT / 论文 / 漫剧三大技能，且会长新技能。
**如果编排写在 Python 里，每加一个技能就要改主程序 —— 那「技能可插拔」就是假的。**
已实现为：Harness 循环不知道"漫剧"是什么，它只做四件事 ——
把技能文本 + 上下文交给模型、执行模型要的工具、校验**数据化的**验收标准、落盘并打检查点。

对应到代码：`app/harness/runner.py` 里没有任何技能名，阶段顺序/验收标准/是否要人确认全部读自 `skills/*/manifest.yaml`。

### 9.1 技术选型（已定）

| 层          | 选型                                                  | 决策 |
| ---------- | --------------------------------------------------- | -- |
| Harness 执行内核 | **自研薄内核**（D1 的回退路径，见下方说明）；可选再接 OpenHarness | D1 |
| 后端         | **Python / FastAPI**（asyncio）                       | D2 |
| 前端         | **React + Vite + Tailwind**（SPA，后端独立服务）             | D3 |
| 元数据存储      | **开发期 SQLite → 生产 Postgres**（SQLAlchemy 统一抽象，只改连接串） | D4 |
| 产物存储       | **本地文件系统 → 生产对象存储**（`StorageAdapter` 切换）            | D4 |

> **关于 D1 的落地说明（重要）**：原决策是"OpenHarness 作内核"。动手后确认两件事：
> ① PyPI 上的 `openharness` 是**另一个不相关**的包（作者 Sergio Rovira，17KB 的智能体训练环境库）；
> 港大 HKUDS 的需从 GitHub 源码装，而本机 GitHub 直连不通、且**没有 git**（只能走镜像下 zip）。
> ② 更关键的：这两个参考项目（OpenHarness / OpenMontage）本质是**跑在 AI 编程助手里的"技能包"**，
> 不是可直接被后端调用的 Python 库。我们的 Harness 就是要**替代那个"AI 编程助手"的角色**，
> 所以它本身必须是我们的进程内实现。
>
> → **M0 直接采用 D1 预设的回退方案（自研薄内核）**。架构设计一字未改，只是内核实现自持：
> Agent 循环、技能加载、工具注册、检查点、门禁、配额、SSE 全部在 `app/harness/` 内实现，
> 约 1200 行。这样也顺带满足了「无中央编排器」的要求 —— 自研内核才能做到**里面没有任何流程逻辑**。

**OpenHarness 与自研层的职责边界**：

| 由 OpenHarness 提供                            | 由我们自研（长出主干之上）                     |
| ------------------------------------------- | --------------------------------- |
| Agent 循环（流式工具调用、退避重试、并行执行）                  | **Run / Step 状态机**（含 Gate 挂起与恢复）  |
| Skill 按需加载（Markdown 技能，兼容 Anthropic Skills） | **技能 manifest 解析 + 阶段编排（DAG）**    |
| 工具注册与执行、MCP 客户端                             | **SSE 事件流接入与断线续传（Last-Event-ID）** |
| 权限治理、生命周期 Hook                              | **产物管理与版本、Checkpoint 落库**         |
| 上下文压缩、token 计量                              | **快/慢双通道调度**（§5.1）                |
| 多模型接入（OpenAI 兼容 / Anthropic）                | **自校验闭环与决策留痕**（§7.3.5 / §7.3.4）   |

> 原则：**能用开源内核解决的，不自己写；凡是「长任务产品」特有的（状态机、关卡、双通道、留痕），必须自己写。**

## 12. 非功能需求

| 维度        | 要求                                         |
| --------- | ------------------------------------------ |

| **并发**    | 单用户同时 N 个 Run（默认 2）；全局队列；阶段间可并行时并行         |
| **安全**    | 每用户数据强隔离；文件类型与大小白名单；沙箱执行；上传路径不可信           |
| **可观测**   | 全事件入库；任一 Run 可完整回放                         |
| **失败处理**  | 阶段失败可重试（指数退避）；重试仍失败则降级为"请求人工介入"而非整体崩溃      |

因此开发期按下述方案落地：

- 开发期用 **SQLite**，保证「克隆即能跑」，开发零阻塞
- 但**抽象层保真**：统一走 SQLAlchemy，**业务代码不写任何 Postgres 专有特性**  
  （JSON 字段用通用 `JSON` 类型而非 `JSONB`；不用数组类型；不依赖方言专属函数）
- 上线时**只改连接串**即可切到 Postgres；产物存储同理（`StorageAdapter`：本地实现 → S3 实现）
- 代价：上线前需做一次兼容性回归测试

> 建议开发顺序：**M0 + M0.5，且只做「漫剧」一个技能的快通道**。

## 附录 A：为什么不是"一个超级 Agent"

我们**不做**"给我一句话，AI 自己搞定一切"的黑盒。理由：

1. 长任务里 **20% 的关键判断决定了 80% 的质量**（选题、大纲、分镜），这些必须由人拍板 → Gate 是刚需；
2. 黑盒失败时用户**无法介入、无法定位、无法复用**；
3. 可复用的不是"Agent 的聪明"，而是"**技能的流程**" → 所以技能包要显式、可读、可编辑、可分享。

## 附录 B：参考的开源 Harness 生态

- **OpenHarness**（HKUDS）：Python、约 1.2 万行、43 工具、Markdown 技能按需加载、多级权限、生命周期 Hook、兼容 Anthropic Skills 生态
- **DeepSeek Harness**：基于 Cordis 插件系统，"一切皆插件"，Skill/沙箱/调度/UI 皆可配置组合，带 Trajectory 轨迹追踪与恢复回放
- **Codex Harness**（OpenAI）：JSON-RPC 连接 App-Server，原生 HITL 审批，内置沙箱，模型无关编排层
- **AgentScope HarnessAgent**：Workspace + 长期记忆 + 子 Agent + 沙箱 + Skill 组合 + Plan Mode
- **LangChain deepagents**：batteries-included，规划/文件/子 Agent 开箱即用

> 共识：Harness = **模型之外的执行层**（循环、工具、上下文、权限、沙箱、持久化、可观测）。我们复用的是这套骨架，而不是某个具体实现。

### C.3 从 ppt-master 继承的 5 项设计

1. **`harness + model = agent`**（README 原话）—— 印证了我们对 Harness 的理解，也印证了它该是"执行环境"而非"编排器"
2. **Strategist / Executor 双角色** —— 规划与执行分离，避免"边想边做"导致的跑偏
3. **`design_spec.md`（人读）+ `spec_lock.md`（机器可读执行契约，每页必须重读）** —— 解决长上下文漂移
4. **八项确认打包成一次 BLOCKING 门禁 + 一键模式不提问自动锁推荐值** —— 与我们的「零输入可跑」完全一致
5. **设计哲学：「AI 是你的设计师，不是完工师」** —— 直接决定了 D14 的措辞选择
